# Executable documentation pipeline

User guides and their media are generated by running the application. A feature
owns one Rust scenario and one Markdown template, registered together in the
documentation harness. The same required `just docs check` verifies still images,
animations, bindings, assertions, and the complete generated file inventory.
There is no manually maintained screenshot or animation path.

`just docs update` and `just docs check` run on the native host: Metal on macOS,
an available Vulkan adapter on Linux. The same scenarios, capture code, encoders,
and exact artifact checks serve both local development and CI. No container or
CI marker is required for local work. A missing capture adapter is an error.

The manifest identifies the renderer profile that produced the guide. Profiles
are not interchangeable: Metal and lavapipe pixels may differ. Exact comparison
rejects a profile mismatch with an explicit diagnostic, without skipping images.
Switching the baseline renderer is an intentional `update` followed by review.

`just ci-docs check/update` explicitly opts into the pinned Ubuntu environment
in [Dockerfile](../../tools/ci/Dockerfile), launched by
[ci_runner.py](../../tools/ci_runner.py). That optional path uses
Mesa lavapipe and separate caches; only its update mode mounts the guide writable.
The current baseline is Metal. The Linux baseline gate remains unresolved before
first push; see [verification](../development.md#verification-and-git-hooks).

The implementation lives under [src/documentation](../../src/documentation/).
Feature scenarios are in [scenarios](../../src/documentation/scenarios/), their
Markdown sources are in [docs/templates](../templates/), and generated pages,
media, and the manifest are in [docs/guide](../guide/). Register a scenario module
in [mod.rs](../../src/documentation/mod.rs) and its feature/template pair in
[features.rs](../../src/documentation/features.rs). Engineering decisions live
here in `docs/architecture`; research stays separate in `docs/research`.

The generated guide is user-facing. Its links must resolve within the guide;
repository-owned, GitHub-hosted documents such as the root README, TODO,
contributor instructions, and engineering notes may link to it, but the guide
must not link back to them. Link validation rejects those outbound references.

## Local browser preview

`just docs` serves the existing guide on a loopback HTTP server and opens a
browser. It uses Python 3's standard library and a vendored Docsify 5 runtime;
all scripts and styles load locally. The generated guide index supplies the
sidebar, and pages use their existing Markdown links and WebP assets, including
animations. There is no second content tree or separate site build.

This presentation layer does not execute scenarios, regenerate artifacts, or
approve a baseline. After `just docs update`, refresh the browser to see the
changed output. `just docs check` still performs the strict replay described
below. `just docs-preview-test`, included in `just verify`, checks the server
routes and local browser assets independently of the GPU pipeline.

Keep this preview disposable. The pipeline continues to produce ordinary
Markdown and media that a future website can consume; the local viewer does not
commit N3 to a production documentation framework. See
[development](../development.md#documentation-is-executable) for server options.

## One replay and rendering path

`Session` delivers pointer and keyboard events to the real `WorkspaceUi` and its
shared shortcut dispatcher. Native number-key source metadata travels alongside
the egui key events, so top-row and numpad keys remain distinct. Text events stay
separate from physical key events; a native key/text pair must not type twice.

Native scroll, pinch, and twist arrive outside egui's normal pointer routing.
[navigation_events](../../src/input/navigation_events.rs) represents those inputs with logical-point or wheel-line
deltas, native pinch deltas, rotation degrees, modifiers, and scroll phases.
The native window and documentation session call the same navigation router.
It respects pointer location, window focus, floating UI, open menus, a pending
view pie, and active mouse gestures. Active editor pointer gestures and property
edits exclude camera input; released transform previews allow navigation while
retaining their edit baseline. Blocked scroll input clears its gesture latch.

Replay derives the corresponding egui event from that same navigation event,
using egui-winit's unit/sign conversions. The virtual input overlay observes the
events; scenarios cannot independently paint a gesture and apply a different
camera action. Rejected input can still have a cue, just as a key pressed over
an input field can be visible without activating a viewport shortcut. The
scenario must assert whether the application accepted or rejected its effect.

Modifier-only changes are real replay steps. Shift ownership must survive a
finger-to-momentum phase handoff and end when Shift is released. Focus loss and
pointer exit have explicit events; a screenshot never invents those events.

Fixture installation and deliberately authored initial documents remain setup
boundaries. An illustrated operation must then use the input path. Replaying a
gesture tests its routing and result, not macOS's recognition of human fingers.

## Time and media

The scenario clock is explicit. `frame(events, elapsed)` displays the previously
completed frame for `elapsed`, advances the camera and cue clocks, then delivers
the next sample. Zero-time input edges and egui layout retries produce no extra
animation frames. Captures do not sleep, read wall-clock time, release keys, move
the pointer, or manufacture intermediate geometry.

`capture_clip` scopes one recorder around ordinary scenario actions. `wait`
samples empty input while camera transitions and cue fading continue.
`move_pointer` samples a path while the already-pressed button remains held;
`pointer_button` supplies explicit press/release edges. A trailing wait makes the
final result visible. The default sample interval is 50 ms; clips use integer
millisecond holds of at least 11 ms to avoid ambiguous very short WebP playback
delays. A large unsampled clock jump during recording fails.

The scene renderer, egui compositor, and paint-only tutorial overlays render the
same frames as still documentation. `Capture::read_frame` returns completed
RGBA pixels without advancing application state. A still checkpoint requires a
settled camera; an animated clip intentionally permits transitions.

## Canonical guide composition

Each scenario starts with visible UI and the same ephemeral saved layout: both
side panels are 240 logical points wide, and the unscaled application canvas is
1920 × 1080 at one pixel per point. `SavedLayout` stores panel widths only; the
ordinary session controls UI visibility. Scenarios can then change the real
layout through the normal UI when that change is what they illustrate. The saved
layout is capture setup, separate from documents, global preferences, and edit
history; it is not a versioned workspace format.

The session renders once to establish egui's initially appearing Areas, then
advances its explicit clock through the current style's animation duration,
rounded up to a whole millisecond, and settles again. This one-time startup
step makes the toolbar fully visible before a scenario begins. Ordinary
`settle()` and capture calls still advance no time, including during held
gestures.

To use a standard composition around a special layout and then restore it
within a scenario:

```rust
use crate::workspace_ui::SavedLayout;

let previous = s.state.save_layout(&s.ctx);
s.state.apply_saved_layout(&s.ctx, SavedLayout::DOCUMENTATION);
s.settle()?;
s.capture_tutorial("example")?;
s.state.apply_saved_layout(&s.ctx, previous);
s.settle()?;
```

The ordinary guide baseline selects Light explicitly, independent of the host
appearance. The appearance guide deliberately switches between Light and Dark
through Preferences to illustrate both. The shared, static
[window-frame template](../../src/documentation/presentation.rs) surrounds
the captured application pixels for every still and animated asset. This
decorative frame is generated by the same capture path; it does not replace the
application UI or change input coordinates. The manifest records the app canvas
and final media dimensions so the layout and frame remain reviewable.
The replay context explicitly selects macOS for key labels and UI behavior, so
the Ubuntu renderer still illustrates the Mac application. The static window
frame and canonical input bindings also keep that presentation independent of
the host OS.

The frame uses the macOS 27 reference's approximate control diameter, spacing,
and tighter corner radius, with rounded bottom corners. Its optional cast shadow
is disabled for the guide, so the saved image has no shadow or outside margins;
the browser can apply its own shadow. Apple does not publish fixed pixel dimensions for this window style;
the values are isolated in the frame template and are visual estimates from a
2x reference. The title-bar height varies with native window configuration.
Exact macOS 27 glass materials and dynamic control effects remain in the
repository backlog.

Still and animated assets use lossless WebP. The animated encoder compresses
changed regions with the existing WebP codec and writes standard replacement
frames. Identical consecutive samples extend a hold; other frames replace only
the exact changed rectangle, with WebP-aligned offsets. This preserves UI text,
selection colors, transparency, and timing without palette quantization. Only
one previous RGBA canvas is retained. Authored sample count, duration,
canvas memory, and encoded size have explicit limits. Encoding cannot advance
the application clock or create input. A clip must contain at least two sampled
frames, and its behavior needs intermediate and final assertions; frame count
alone does not demonstrate the interaction. The manifest distinguishes authored
samples from encoded frames; lossless frame coalescing does not change the
scenario clock or remove input steps.

## Authoring an animated interaction

This scenario uses the actual API in
[tutorial.rs](../../src/documentation/tutorial.rs). It holds the canonical pan
shortcut and the primary button while moving the pointer, asserts that the camera really panned, then
releases both inputs and leaves time to see the result.

```rust
use super::{ClipSpec, Result, Session};
use crate::controls::Control;
use egui::PointerButton;
use std::time::Duration;

pub fn run(s: &mut Session<'_>) -> Result<()> {
    s.load_fixture("cube-quads.obj")?;
    s.click(Control::ToolMove)?;
    s.hover(Control::Viewport)?;
    let destination = s.state.viewport.center() + egui::vec2(80.0, -35.0);
    let camera = s.state.camera.view_projection(s.state.aspect());
    let document = s.state.editor.document.clone();

    s.capture_clip("hand-pan", ClipSpec::default(), |s| {
        s.callout(Control::ToolMove, &format!("Hold {} and drag to pan.", s.shortcut_label("navigation.pan")?))?;
        s.wait(Duration::from_millis(500))?;
        s.shortcut_down("navigation.pan")?;
        s.pointer_button(PointerButton::Primary, true)?;
        s.move_pointer(destination, Duration::from_millis(900))?;
        s.require(
            s.input.is_pressed(PointerButton::Primary)
                && s.state.camera.view_projection(s.state.aspect()) != camera,
            "The held pointer gesture pans the camera",
        )?;
        s.pointer_button(PointerButton::Primary, false)?;
        s.shortcut_up("navigation.pan")?;
        s.clear_callout()?;
        s.wait(Duration::from_millis(500))
    })?;
    s.require(
        s.state.editor.document == document && !s.state.hand_tool_active(),
        "The tutorial releases the hand tool without editing geometry",
    )
}
```

Reference that asset with `{{animation:hand-pan}}` in the feature's matching
template. Run `just docs update`, review the generated guide and playback, then
run `just docs check`. The existing
[hand-tool scenario](../../src/documentation/scenarios/hand_tool.rs) also verifies
constant scale/orientation and the case where Space is released before the mouse
button. Use `click_path(&[Control::ViewMenu, Control::Frame])` when an operation
requires opening a menu; do not call the underlying camera action from a tutorial.

## Live targets and annotations

Controls have stable identities but use their actual displayed labels, bounds,
enabled state, and parent scopes. A `control` template binding must be witnessed
in that feature's run. A missing or ambiguous control fails. `click` acts only on
an already visible control; `click_path` describes an explicit sequence of
controls and begins at its deepest visible member. Menu locations are not
duplicated in an implicit harness routing registry.

Keep keyboard instructions and menu locations bound to their source:

```markdown
Press {{shortcut:tool.move}}, then {{shortcut:transform.axis-x}}.
Choose {{control:preferences.open}} to open Preferences.
```

`{{shortcut:semantic-id}}` reads the same
[binding definitions](../../src/input/bindings.rs) that production input routing
uses. It renders each key with `<kbd>` markup, including modifiers and the
distinction between number-row and numpad keys. Changing that definition and
regenerating the guide updates the instructions without a second keymap. UI
shortcut hints read this registry too; control names do not contain copied keys.

`{{control:id}}` renders the witnessed menu path as inline `<code>`, preserving
the actual UI names and nesting. Do not write those paths or action shortcuts
directly into guide prose. An unknown shortcut or an unwitnessed control fails
generation. The manifest records the canonical bindings and each feature's used
shortcut references.

For an illustrated shortcut, use `Session::shortcut`, `shortcut_down`, or
`shortcut_up` with the binding ID. These helpers synthesize the binding's real
input events, including native number-key metadata, through the normal router;
they do not dispatch the action directly. A prose reference need not replay the
shortcut separately if its feature already demonstrates the same behavior, but
an illustrated interaction must use the input path.

Literal text-entry keys are a separate case: `{{key:Backspace}}` describes
editing a number, not the remappable Delete action. `{{modifier:shift}}`,
`{{modifier:control}}`, `{{modifier:command}}`, and `{{modifier:alt}}` describe
physical gesture modifiers. Both render as `<kbd>` as well. Use a semantic
shortcut reference whenever the instruction invokes an application action.

A callout binds to a live control ID. Each rendered frame resolves its current
bounds and label, so resizing or moving that control moves the annotation. A
missing target fails instead of leaving an arrow pointing at an old coordinate.
Callouts and virtual input only paint; they cannot capture pointer or keyboard
input, alter focus, or change document state. Clean images hide these overlays
without changing hover or held input. Authors explicitly move the pointer if a
particular composition requires a different hover state.

Templates distinguish `{{image:name}}` and `{{animation:name}}`; using the wrong
media kind, referencing absent media, or producing unreferenced media fails.
Both kinds remain `.webp` assets and are checked through the same generated tree.

## What the checks establish

Generation runs every scenario, assertion, capture, and binding check before
writing artifacts. `check` is read-only. The full tree comparison catches changed
Markdown, image or animation bytes, missing files, and orphan files. The manifest
records witnessed control paths, scenario values and assertions, rendering
profile, and each recorded frame's time and input evidence. The runtime reports
the selected adapter and driver in its command output. Removing an
obsolete artifact is explicit; generation does not silently approve deletion.
`just test` and `just verify` run the strict artifact test on the native host.
The pre-push hook calls the same native verifier. `just ci` explicitly selects
the Ubuntu environment; it has no exemption from exact media comparison.

This is a strict reproducibility and behavioral contract, not proof that arbitrary
prose is correct. A `value` binding must be backed by a meaningful assertion in
its scenario. Freeform explanations and callout captions still require review.
Likewise a passed assertion does not guarantee a legible tutorial: review the
rendered media for occlusion, pacing, contrast, and useful framing.

Baselines use a fixed canvas, bundled fonts, and explicit time. Renderer profiles
are recorded; arbitrary drivers or devices are not assumed to match their pixels.
A missing adapter fails rather than skipping the check. Updating a baseline requires
reviewing its generated changes, including decoded animation frames and timing.
A Docker build alone does not validate a regenerated baseline. Native file
dialogs, physical gesture recognition, device feel, and OS delivery still need
focused native/manual checks.

The harness stays deliberately small: Rust scenarios, shared input adapters,
one clock, one renderer, live controls, and bounded media encoders. It does not
introduce a separate tutorial application, a second command implementation, or
a generic scripting language.
